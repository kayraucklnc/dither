= Transit

Transit extensions render a live public transport departure board. They are a
distinct extension kind: there are no exchanges to configure, because the
settings name a country, a city, and a provider, and the provider knows how to
answer.

Milan, served by {trenord_link}, is the only city supported today.

toc::[]

== Setting one up

. Package the preset: `bundle exec rake transit:preset` writes
  `tmp/milan-trenord.zip`.
. Visit the _Extensions_ page and import that archive.
. Edit the extension and set your route under the _Data_ tab:
+
[source,json]
----
{
  "values": {
    "origin": "MILANO CERTOSA",
    "destination": "MILANO CADORNA",
    "lead_time": 30,
    "limit": 5
  }
}
----
. Select the model(s) to build for, then _Build_.

The example route is a starting point, not a default worth keeping. Station
names must match Trenord's own spelling; the catalog endpoint below answers
them, and the settings component autocompletes against it.

== Settings

All settings live under `data.values`, which is the same place the ordinary
custom fields UI writes to, so a transit extension stays editable by hand and
will pick up a richer form when one lands.

[options="header"]
|===
| Key | Default | Meaning
| `country` | `it` | Only Italy today.
| `city` | `milan` | Only Milan today.
| `provider` | `trenord` | Only Trenord today.
| `origin` | — | *Required.* Station to depart from.
| `destination` | — | Required for journey planners. See below.
| `lead_time` | `0` | Minutes to reach the platform. Trains leaving sooner are hidden.
| `limit` | `5` | Departures to show, 1 to 20.
| `transfers` | `1` | Maximum changes, 0 to 5.
| `language` | `en` | `en` or `it`, used for service alerts.
| `title` | — | Overrides the heading.
| `show_platform` | `true` | Platforms only publish close to departure.
| `hide_cancelled` | `false` | Cancellations are worth seeing.
|===

The time zone is not a setting. It comes from the catalog, and it matters:
providers quote local wall clock times, while a self-hosted server usually runs
in UTC. Asking Trenord for "21:28" from a UTC box returns trains from two hours
ago.

There is no `layout` setting either. What this extension can render is declared
rather than chosen; see {views_link}.

== Views

Four shapes, one template, sharing one icon set:

[options="header"]
|===
| View | Size range | Shows
| `full` | 400–1600 × 300–1200 | Next train large, then the rest as a list.
| `horizontal` | 400–1600 × 96–220 | A row of chips, the next one inverted.
| `vertical` | 180–360 × 300–1200 | A column of departures.
| `overlay` | 220–420 × 88–160 | One train, inverted, over other content.
|===

Preview any of them at `/extensions/:id/preview?view=vertical`.

== Liquid

A transit extension renders with a top-level `transit` key:

[source,liquid]
----
{{ transit.origin }} to {{ transit.destination }}, read at {{ transit.queried_at }}

{% for departure in transit.departures %}
  {{ departure.line }} {{ departure.number }} to {{ departure.direction }}
  {{ departure.expected }} (scheduled {{ departure.scheduled }})
{% endfor %}
----

`transit.departures` entries carry `line`, `number`, `direction`, `scheduled`,
`expected`, `delay`, `delayed`, `platform`, `platform_actual`, `arrival`,
`duration`, `changes`, `direct`, `cancelled`, `live`, `day_offset`, and a
one-word `status`.

`transit.alerts` carries the provider's service notices as `severity`, `title`,
and `message`, with the HTML stripped. The bundled template leaves them out —
Trenord always publishes at least one — but they are there to use.

== Trenord

=== The endpoints

Neither needs authentication.

[options="header"]
|===
| Endpoint | Answers
| `/mia/bff/hafas/v2` | Journeys. AES-256-ECB encrypted.
| `/mia/v2/stazioni_v2/` | The station registry. Plain JSON.
|===

The registry supports a Mongo style `_q` filter, so a name search is one
request. It is fetched once per process and filtered in memory, which makes a
typeahead free and means Trenord sees roughly one request a day for it.

=== Decryption

The journey planner's body is AES-256-ECB/PKCS7 under a key that is the raw
SHA-256 digest of a passphrase shipped in Trenord's own JavaScript bundle. It
is obfuscation rather than security.

The passphrase is the `trenord_passphrase` setting rather than a constant,
because it is the one fragile part: a new bundle with a new passphrase breaks
decryption silently. Recovery is to re-fetch
`fileadmin/templates/js/web-components/elements/trenord-web-components.js`,
grep for `,Q="[^"]+"`, and set `TRENORD_PASSPHRASE`. The extension reports the
failure rather than rendering a stale board.

=== It is a journey planner, not a board

`hafas/v2` needs a destination, so a transit extension is always "trains from
here towards there" rather than "everything leaving here". No all-directions
station board endpoint has been found.

The planner answers roughly five journeys per call, so a board asking for more
walks forward in time, one request per page, up to four. A default sized board
never pages.

=== Be modest

The site sits behind Akamai. Aggressive polling from one address invites a rate
limit or a challenge. The preset schedules every five minutes, which is roughly
one request per refresh; the browser-ish headers on each request are load
bearing and should stay.

== Adding a city

. Add the city and its provider to `app/aspects/transit/catalog.rb`, including
  the time zone.
. Add a provider under `app/aspects/transit/providers/`, answering `#board` and
  `#stations`.
. Route to it from `Aspects::Transit::Finder`.

Everything above the provider — settings, normalization, views, the settings
component — is provider agnostic. A provider's job is to answer a `Board` of
`Departure` structs and a list of `Station` structs.

See also: {extensions_link} and {views_link}.
